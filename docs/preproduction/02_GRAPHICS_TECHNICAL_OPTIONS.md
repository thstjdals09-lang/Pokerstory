## 1. 그래픽 스타일과 기술적 구현 방식은 다른 문제입니다

두 가지는 자주 섞여서 이야기되지만 따로 결정할 수 있습니다.

| 구분 | 무엇을 정하는가 | 예시 |
|---|---|---|
| **그래픽 스타일** (아트 방향) | 화면이 어떤 느낌으로 보이는가 | 픽셀아트, 손그림 일러스트, 수채화풍, 플랫 벡터, 로우폴리, 툰 셰이딩 |
| **기술적 구현 방식** (렌더링 구조) | 공간, 좌표, 깊이, 카메라를 어떻게 처리하는가 | 2D 탑다운, 2D 아이소메트릭, 2.5D, 3D |

같은 구현 방식이라도 스타일은 다양하게 고를 수 있습니다.

| 구현 방식 | 가능한 스타일 예 |
|---|---|
| A. 2D 탑다운 | 픽셀아트, 손그림 일러스트, 벡터 |
| B. 2D 아이소메트릭 | 픽셀아트(아이소 픽셀), 프리렌더 일러스트, 3D를 렌더링해 만든 2D 스프라이트 |
| C. 2.5D | 3D 배경 + 픽셀 캐릭터, 3D 배경 + 일러스트 캐릭터, 2D 레이어 + 원근 연출 |
| D. 스타일라이즈드 3D | 툰 셰이딩, 로우폴리, 손그림 텍스처 3D |

**결정 순서:** [권고] 구현 방식을 먼저 정하고 스타일을 정하는 편이 좋습니다. 구현 방식이 엔진 선택(01 문서), 에셋 파이프라인, 하우징·커스터마이징의 제작 비용을 결정하기 때문입니다.

## 2. 구현 방식 정의

| 방식 | 정의 | 참고할 만한 기존 게임 유형 |
|---|---|---|
| **A. 2D 탑다운** | 위에서 비스듬히(3/4 시점) 내려다보는 2D. 타일이 정사각형 격자입니다. | 스타듀밸리류, 초기 포켓몬류 |
| **B. 2D 아이소메트릭** | 마름모 격자에 약 30° 투영. 입체감은 있지만 실제로는 2D 이미지입니다. | 고전 심즈·경영 시뮬레이션류 |
| **C. 2.5D** | 이 용어는 뜻이 넓어서 아래 두 가지로 나눕니다. | |
| C-1. 3D 공간 + 2D 캐릭터 | 3D로 만든 마을에 빌보드 스프라이트 캐릭터를 둡니다. | HD-2D류, 돈스타브류 |
| C-2. 2D + 깊이 연출 | 2D 레이어에 원근 스케일과 패럴랙스를 줍니다. | 사이드뷰 어드벤처류 |
| **D. 스타일라이즈드 3D** | 캐릭터와 배경 모두 3D 모델이고, 사실감보다 귀여운 표현을 우선합니다. | 동물의숲류 |

> C-2는 이 프로젝트처럼 마을을 자유롭게 걸어다니는 구조에는 잘 맞지 않아서, 아래에서 C는 **C-1 기준**으로 설명합니다.

## 3. 항목별 비교 [조사]

### 3.1 캐릭터 이동과 애니메이션

| 방식 | 구현 | 제작 비용과 제약 |
|---|---|---|
| A | 2D 물리 바디와 타일 충돌. 방향별 스프라이트 애니메이션 | 보통 4방향(좌우 반전으로 3방향만 그림) 또는 8방향이 필요합니다. 방향 수 × 동작 수 × 프레임 수만큼 그림이 늘어납니다. |
| B | 2D 이동에 아이소 좌표 변환. 방향별 스프라이트 | 아이소는 대각선 4방향이나 8방향이 기본입니다. 좌우 반전은 쓸 수 있지만 위·아래 방향은 따로 그려야 합니다. 이동 방향과 키 입력 방향이 45° 어긋나서 조작감을 조정해야 합니다. |
| C-1 | 3D 물리 바디 + 카메라를 향하는 스프라이트 | 방향별 스프라이트는 A와 같습니다. 카메라가 회전하면 보이는 방향을 다시 계산해야 합니다. 조명과 그림자를 스프라이트에 맞추는 셰이더 작업이 필요합니다. |
| D | 3D 캐릭터, 스켈레톤 애니메이션 | 방향 수 제한이 없고 애니메이션 하나를 모든 방향에 씁니다. 대신 모델링, 리깅, 애니메이션 제작 능력이 필요합니다. 공용 리그를 쓰면 애니메이션을 여러 캐릭터에 재사용할 수 있습니다. |

### 3.2 마을 제작과 건물 배치

| 방식 | 구현 | 제약 |
|---|---|---|
| A | 타일맵 레이어(바닥, 장식, 충돌) + 건물 스프라이트 | 가장 단순합니다. 건물 외벽만 그리고 내부는 별도 씬으로 만드는 것이 일반적입니다. |
| B | 아이소 타일맵 + 깊이 정렬 | **깊이 정렬이 가장 큰 문제입니다.** 크기가 여러 칸인 건물과 캐릭터의 앞뒤 관계가 쉽게 틀어집니다. 건물을 여러 조각으로 나누거나 정렬 기준점을 따로 지정해야 합니다. |
| C-1 | 3D 지형·건물 모델 배치 (GridMap 등 모듈형 조각) | 모듈형 3D 조각을 쓰면 배치가 빠르지만, 조각 세트를 처음 만드는 비용이 큽니다. |
| D | C-1과 같음 | 조명, 그림자, 후처리로 분위기를 만드는 작업이 추가로 필요합니다. |

### 3.3 실내외 공간 전환

| 방식 | 일반적 구현 | 비고 |
|---|---|---|
| A | 문에 들어가면 별도 씬으로 전환(화면 페이드) | 구현이 가장 쉽습니다. 실내외를 끊김 없이 이어 보이게 하려면 지붕을 투명하게 하는 등 추가 처리가 필요합니다. |
| B | 별도 씬 전환, 또는 벽·지붕을 잘라 보여 주기 | 잘라 보여 주기를 택하면 벽마다 잘린 버전 그림이 필요합니다. |
| C-1 / D | 별도 씬 전환, 또는 같은 공간 안에서 카메라와 지붕 투명화로 처리 | 끊김 없는 전환이 가능하지만, 실내 조명 전환과 카메라 충돌 처리가 필요합니다. |

[미정] 끊김 없는 전환 여부는 NPC 스케줄 시스템(03 문서 2절)에도 영향을 줍니다. 공간이 씬 단위로 나뉘면 화면 밖에 있는 NPC를 따로 시뮬레이션해야 합니다.

### 3.4 NPC 이동과 상호작용

| 방식 | 경로 탐색 | 상호작용 판정 |
|---|---|---|
| A | 2D 내비게이션 메시 또는 격자 A* | 가까운 거리 + 바라보는 방향으로 판정합니다. 가장 단순합니다. |
| B | 아이소 좌표의 격자 A*. 표시 좌표와 논리 좌표를 변환해야 함 | 겹쳐 보이는 대상 중 무엇을 선택할지 모호해집니다(클릭·터치 시). |
| C-1 / D | 3D 내비게이션 메시 | 3D 공간에서 판정합니다. 카메라 각도에 따라 대상이 가려지는 문제가 있습니다. |

공통 난제: 좁은 문과 골목에서 NPC끼리 막히는 문제, 플레이어가 길을 막는 문제입니다. 회피 기능은 엔진이 제공하지만 조정 작업이 필요합니다.

### 3.5 캐릭터 커스터마이징

[미정] 기획서 Q7에서 커스터마이징은 필수 코어로 확정되지 않았습니다. 범위에 따라 제작 비용이 크게 달라집니다.

| 방식 | 구현 | 비용이 커지는 구조 |
|---|---|---|
| A / B / C-1 (스프라이트) | 부위별 스프라이트 레이어(몸, 머리, 상의, 하의, 모자 등)를 겹쳐 그림. 색은 팔레트 교체 셰이더로 처리 | **파츠 1개를 추가할 때마다 모든 방향 × 모든 동작 × 모든 프레임을 그려야 합니다.** 예: 4방향 × 동작 6종 × 평균 6프레임 = 파츠 1개당 144프레임. 아이소 8방향이면 두 배입니다. |
| D (3D) | 메시 교체, 블렌드셰이프(체형·표정), 머티리얼 색 변경 | 파츠 하나를 공용 리그에 맞춰 만들면 모든 애니메이션에 자동으로 적용됩니다. **파츠 수가 늘어날수록 3D가 유리해집니다.** 대신 옷이 몸을 뚫고 나오는 문제를 처리해야 합니다. |

색만 바꾸는 커스터마이징은 모든 방식에서 저렴합니다(팔레트·셰이더). 형태가 다른 파츠를 추가하는 것이 비쌉니다.

### 3.6 가구 배치와 하우징

| 방식 | 구현 | 제약 |
|---|---|---|
| A | 격자 배치, 충돌 칸 점유, 벽 부착 오브젝트 레이어 | 가장 단순합니다. 회전이 필요하면 가구마다 방향별 그림이 필요합니다(보통 2~4개). |
| B | 아이소 격자 배치 | **가장 어렵습니다.** 여러 칸짜리 가구의 깊이 정렬, 회전 시 방향별 그림, 벽 가림 처리가 모두 필요합니다. 가구 위에 소품을 올리는 경우 정렬 규칙이 더 복잡해집니다. |
| C-1 | 3D 격자 배치 + 3D 가구 | 회전이 자유롭고 정렬 문제가 없습니다. 가구는 3D 모델이어야 합니다. 캐릭터만 2D라서 가구와 크기감이나 느낌이 맞지 않을 수 있습니다. |
| D | 3D 격자 배치 | 구현이 가장 자연스럽습니다(동물의숲 방식). 가구 수만큼 3D 모델이 필요합니다. |

공통 기술 과제: 배치 가능 여부 판정, 겹침·쌓기 규칙, 회전, 되돌리기, 저장 형식, 터치 조작(드래그·회전 버튼), 가구 수가 많아질 때의 성능.

### 3.7 카메라와 화면 구성

| 방식 | 카메라 | 해상도 대응 |
|---|---|---|
| A | 고정 각도, 캐릭터 추적, 줌 제한적 | 픽셀아트는 정수 배율 스케일링이 필요합니다. 16:9와 모바일 세로·가로 비율 차이를 보이는 영역 확장으로 처리합니다. |
| B | 고정 각도, 추적. 회전하려면 그림이 4배 필요 | A와 같습니다. |
| C-1 | 고정 각도 또는 제한된 회전. 줌 자유 | 3D이므로 해상도에 자유롭습니다. 스프라이트 캐릭터의 선명도를 관리해야 합니다. |
| D | 자유 또는 제한 회전, 줌 | 해상도에 자유롭습니다. 벽이 캐릭터를 가리지 않도록 처리해야 합니다. |

### 3.8 에셋 제작 난이도

| 방식 | 필요한 역량 | AI 이미지 생성 활용도 |
|---|---|---|
| A | 2D 드로잉 또는 픽셀아트, 타일셋 설계 | 컨셉 아트, 초상화, 아이템 아이콘, 배경 참고에는 유용합니다. **타일 이음새와 애니메이션 프레임 일관성은 약해서** 후보정이 필수입니다. |
| B | A + 아이소 투영 규칙 준수 | A보다 어렵습니다. 생성 이미지의 각도가 아이소 규칙과 어긋나는 경우가 많습니다. |
| C-1 | 3D 모델링(배경) + 2D 캐릭터 | 3D 생성 AI로 소품 초안을 만들 수는 있지만, 토폴로지 정리와 텍스처 통일 작업이 필요합니다. |
| D | 3D 모델링, 리깅, 애니메이션, 셰이더 | 가장 많은 역량이 필요합니다. 3D 생성 AI의 결과물은 리깅과 애니메이션이 필요한 캐릭터에 바로 쓰기 어렵습니다. |

**AI 생성 에셋의 공통 제약 [조사]**
- Steam은 AI 생성 콘텐츠 사용 여부를 스토어 제출 시 공개하도록 요구합니다.
- 도구마다 상업 이용 조건이 다릅니다. 에셋별로 생성 도구, 프롬프트, 라이선스를 기록해야 합니다(04 문서).
- 스타일 일관성 유지가 가장 어렵습니다. 캐릭터 시트나 스타일 기준 이미지를 먼저 확정해야 합니다.

### 3.10 제작 기간에 영향을 주는 요소

제작 기간은 구현 방식보다 **에셋의 개수와 곱셈 구조**에 더 크게 좌우됩니다.

```
캐릭터 스프라이트 수 ≈ 캐릭터(또는 파츠) 수 × 방향 수 × 동작 수 × 동작별 프레임 수
가구 스프라이트 수   ≈ 가구 수 × 회전 방향 수 (× 색상 변형, 셰이더로 처리하지 못할 경우)
3D 방식            ≈ 모델 수 + 공용 애니메이션 수 (방향 곱셈 없음, 대신 개당 단가가 높음)
```

| 요인 | 기간을 늘리는 방향 |
|---|---|
| 방향 수 (4 → 8) | 2D에서 캐릭터 그림이 약 2배 |
| 커스터마이징 파츠 수 | 2D에서 파츠마다 전체 애니메이션을 다시 그림 |
| 가구 회전 | 2D에서 가구마다 2~4배 |
| 주민 수 | 2D·3D 모두 캐릭터마다 비용 발생. 커스텀 캐릭터와 파츠를 공유하면 줄일 수 있음 |
| 낮밤 조명 | 2D는 색조 변경 셰이더로 저렴하게 가능. 3D는 조명 설정이 따로 필요 |
| 계절·이벤트 변형 | 2D는 타일셋·스프라이트 변형이 필요하고, 3D는 머티리얼 교체로 비교적 저렴 |

## 5. 개발 담당 권고 [권고]

> 개인 의견입니다. 최종 결정은 기획 단계에서 합니다.

- **기술 위험이 가장 낮은 것은 A(2D 탑다운)입니다.** 기획서 방향(아기자기한 마을, 하우징, 수집, 관계)을 모두 수용할 수 있고, 모바일 확장도 가장 쉽습니다. 손그림 일러스트든 픽셀아트든 스타일 선택 폭도 넓습니다.
- **B(아이소메트릭)는 하우징이 중요한 이 기획에서 기술 비용이 가장 큽니다.** 아이소의 분위기가 꼭 필요하다면 "3D로 만들고 고정 아이소 카메라로 보여 주기"(D의 변형)도 대안이 됩니다. 이 방법은 정렬 문제가 사라지는 대신 3D 에셋이 필요합니다.
- **커스터마이징 범위가 넓어질 예정이라면** 2D에서는 파츠마다 비용이 곱절로 늘어납니다. 이 경우 D나 C-1을 진지하게 검토해야 합니다. 커스터마이징 범위를 정하는 것이 그래픽 방식 결정의 핵심 입력값입니다.
- **D(3D)는 3D 에셋을 조달할 방법이 확보된 경우에만 권고합니다.** 에셋 팩, 외주, 직접 제작 등입니다. AI 생성만으로 3D 캐릭터 파이프라인을 채우는 것은 현재 기술로는 위험합니다.
